# Utilizing LLMs in Drug Repurposing

Evaluating LLM agents that query biomedical knowledge graphs for reproducible drug-repurposing research.

## Motivation

In drug research and medicine, an answer is only useful if it is correct and comes out the same every time. AI agents can now read a question, write a Cypher query, run it against a graph database and report the result. This project asks how well, and how reproducibly, current language models do this on a biomedical graph built in 2017.

## The data: Hetionet v1.0

Hetionet integrates data from public biomedical resources into one graph, originally built to predict new uses for existing drugs (Himmelstein et al., *eLife*, 2017).

- **47,031 nodes** of **11 types**, **2,250,197 relationships** of **24 types**
- Stored in Neo4j and queried with Cypher
- Public read-only server: `neo4j.het.io` (Neo4j 3.5.12 Community, no login, reached over the HTTP API)

### Things worth knowing

- The graph contains only **137 diseases** and **755 known treatments**, so coverage is limited by design.
- The data is a **2017 snapshot** and never changes, which suits reproducibility studies.
- The server runs **Neo4j 3.x**, so modern Cypher syntax (for example `EXISTS { ... }` subqueries) is not available. Agents must write older-dialect Cypher.
- Disease names are lowercase (`bile duct cancer`), gene identifiers are numeric, and compound names are capitalised (`Flavoxate`).

## How to run

**Requirements:** [uv](https://docs.astral.sh/uv/) and Git (uv installs Python), plus an API key for an OpenAI-compatible LLM endpoint (see `.env.example`).

```powershell
# 1. Install
git clone https://github.com/jakubradziejewski/reproducible-agents-biomedical-kg.git
cd reproducible-agents-biomedical-kg
uv sync

# 2. Configure. The public Hetionet server needs no credentials; keys are only for hosted models.
cp .env.example .env        # then edit .env. Never commit it.

# 3. Check the database connection and export its schema
uv run python src/explore_schema.py          # writes data/schema.md

# 4. Rebuild the gold questions from the hand-written Cypher
uv run python src/build_gold.py              # writes data/questions.jsonl

# 5. Self-test the evaluator
uv run python src/evaluate.py

# 6. Run agents: one question first, then the whole set with repetitions
uv run python src/run_experiments.py --models qwen3.8-27b --only q01
uv run python src/run_experiments.py --models qwen3.8-27b --reps 3
```

| Option | Meaning |
|---|---|
| `--models a,b` | Keys from `src/models.py` |
| `--only q01,q03` | Run only these questions |
| `--reps N` | Repeat each question N times (repeatability) |
| `--max-steps N` | Max model response turns per run (default 6); a turn may issue multiple tool calls |

The agent is instructed to return its final answer as a JSON array of row objects.
Experiment accuracy is calculated from that final answer, not by selecting the best
intermediate tool call against the gold data. Graph queries are executed only when the
provider returns a native OpenAI-compatible tool call.

## Exploring indirect evidence

[explore_indirect_evidence.py](src/explore_indirect_evidence.py) profiles candidate compounds
against a disease in Hetionet. It reports graph presence, direct-edge status, C-G-D and C-G-G-D
path counts, distinct-gene coverage, candidate overlap and a C-G-D ranking.

```powershell
uv run python src/explore_indirect_evidence.py "vitiligo" Ruxolitinib Methoxsalen Monobenzone
uv run python src/explore_indirect_evidence.py "endogenous depression" Dextromethorphan Bupropion Pramipexole Sertraline Metformin
```

## MCP tools for agent runs

The experiment agent launches the local MCP server in `src/mcp_server.py` over stdio.
It discovers these tools and passes them to the OpenAI-compatible model as tool calls:

- `run_cypher`: execute read-only Cypher against Hetionet (50-row limit);
- `get_graph_schema`: fetch compact labels, relationship directions, and Neo4j 3.5 guidance.
  Detailed property lists are not exposed to the model to avoid unnecessary prompt tokens.

Each run log records per-model-turn prompt/completion token counts and the tools called on
that turn, so token changes can be traced to added conversation context.

The default system prompt is intentionally short. The schema tool is available but not required
for every question. The MCP SDK is installed by `uv sync`.

## Preprocessing and notebooks (Milestone 3)

The project includes offline prompt-context generation based on T2CSS (Wan et al., 2025)
and a separate Cypher validator based on CYGNET (Tomczak, 2026), adapted for Hetionet.
The validator checks vocabulary, relationship direction, and (optionally) server planning.

`src/t2css.py` writes five prompt variants per question to `data/t2css_context.jsonl`.
The runner supports four comparable conditions: baseline, filtered T2CSS context, CYGNET
validation, and both together. T2CSS uses the filtered schema-and-rules prompt; CYGNET
checks each generated query's vocabulary and relationship direction, then asks Neo4j to
`EXPLAIN` it before execution. Failed checks are returned to the agent so it can repair
the query. The runner checks that cached T2CSS prompts match the current gold questions.

```powershell
uv run python src/build_schema.py            # writes data/schema.json (labels and 24 triples with glosses)
uv run python src/t2css.py                   # writes data/t2css_context.jsonl (five prompt variants per question)
uv run python src/run_experiments.py `
  --models qwen3.8-27b,mimo-v2.6-flash-mopd,glm-5.3-flash,qwen3-vl-235b `
  --reps 3 `
  --conditions baseline,t2css,cygnet,t2css_cygnet # 240 runs total
uv run jupyter lab                           # open the notebooks below
```

| Notebook | Shows |
|---|---|
| `notebooks/intro/01_hetionet_cypher_http.ipynb` | Querying Hetionet with Cypher over HTTP, `EXPLAIN`, the old Cypher 3.5 |
| `notebooks/intro/02_agent_tool_calling.ipynb` | How the agent loop and tool calling work, with one run replayed from the pilot log |
| `notebooks/intro/03_embeddings_model2vec.ipynb` | Text embeddings and similarity with model2vec |
| `notebooks/preprocessing/01_t2css_pipeline.ipynb` | One question through all five preprocessing steps, and how the filter behaves on our questions |

The notebooks are committed with their outputs, so they can be read directly on GitHub. Running them does not need an API key. The first run downloads the embedding model `minishlab/potion-base-8M` from Hugging Face.
